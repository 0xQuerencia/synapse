# Local packages, installation and rollback

The release tools create and install local candidate artifacts. They do not publish a release, register services, start inference, edit shell configuration or provide production signing keys. The root MIT/workspace Apache metadata discrepancy and release acceptance gates remain unresolved until the maintainer supplies the required evidence.

Initial installer scope is **Linux x86_64/aarch64** with Python 3.9+ and an OpenSSL version supporting Ed25519 `pkeyutl -rawin`. Installer tests here run on Linux with synthetic native payloads. They do not establish that Synapse inference has been validated on both architectures.

## Build a local development package

Build the actual binary and resolve its toolchain/model tests first. From the repository root:

```sh
python3 scripts/release/package.py \
  --binary target/release/synapse \
  --version 0.2.0-dev \
  --target x86_64-unknown-linux-gnu \
  --output-dir /tmp/synapse-package
```

This writes a deterministic USTAR/gzip archive and a bounded JSON statement with archive SHA-256, byte size, manifest SHA-256, version, target and channel. The archive contains the binary, root LICENSE, manifest and optional `--sbom` inventory. Metadata timestamps/owners are normalized. Source code and model/configuration data are not bundled automatically. Existing output files are never overwritten.

Unsigned development artifacts require both an explicit `--allow-development` and an independently supplied `--sha256` when installed. Reading the digest from an untrusted sidecar does not authenticate its source. Do not distribute development opt-ins as a normal end-user install instruction.

## Signed candidate format

An authorized release operator may add `--channel candidate --signing-key /path/to/private-ed25519.pem`. The tool requires a private, user-owned Ed25519 key and signs the exact statement bytes. The private key is neither copied into the package nor generated by this command. Obtain the corresponding public key through an independently trusted channel; the package does not get to declare its own trusted publisher.

Signature, statement and archive are separate files. A signature authenticates the candidate's origin under the chosen key; it does not settle model rights, license ownership, runtime correctness or release approval. No signed production artifact is claimed by the local test suite.

## Verify a candidate before installation

```sh
python3 scripts/release/install.py verify-artifact \
  /path/to/synapse-VERSION-TARGET.tar.gz \
  --statement /path/to/synapse-VERSION-TARGET.tar.gz.statement.json \
  --signature /path/to/synapse-VERSION-TARGET.tar.gz.sig \
  --public-key /path/to/trusted-release-public.pem
```

The command authenticates the statement, checks the host target, and verifies the bounded archive and every manifest entry in a disposable private directory. It prints the verified manifest and removes its staging files. It has no activation step.

To qualify the actual CLI build locally with a disposable test key and the original offline fixture, use the [low-memory build](development-memory.md) followed by the package smoke check. The smoke check compares the verified package payload's digest with the build and runs that build against eight reference token IDs.

```sh
python3 scripts/low_memory.py build -p synapse-cli
python3 scripts/release/smoke_cli.py --binary target/low-memory/debug/synapse
```

## Install a verified candidate

Use actual paths/version from the produced artifacts:

```sh
python3 scripts/release/install.py --prefix "$HOME/.local/share/synapse" install \
  /path/to/synapse-VERSION-TARGET.tar.gz \
  --statement /path/to/synapse-VERSION-TARGET.tar.gz.statement.json \
  --signature /path/to/synapse-VERSION-TARGET.tar.gz.sig \
  --public-key /path/to/trusted-release-public.pem
```

The prefix must be an empty directory or an existing installer-owned directory, owned by the current user and not group/world writable. No component may be a symlink. No sudo is required. The command prints the explicit executable path; add that directory to PATH yourself if desired.

Verification checks the trusted Ed25519 signature, host target, bounded statement, archive size/hash, manifest hash and every installed file's size/hash/permissions. A private snapshot avoids verifying one file and extracting another. Extraction does not use `extractall`: it accepts a small fixed set of regular files and rejects absolute/traversal paths, duplicates, links, devices, FIFOs, excessive members/bytes and unsafe metadata. Inference is never executed during installation.

## Update and rollback

`update` uses the same archive/statement/signature arguments as `install`. It refuses an active installed native process; stop or drain the worker first. It does not kill running jobs. Downgrades require explicit `--allow-downgrade`; ordinary update cannot silently activate an older semantic version.

The installer stages all files under the same filesystem, verifies them, and then atomically changes the `current` symlink. Earlier releases remain available. A failed package validation leaves the active pointer unchanged. File/directory syncs persist data and pointer changes; local filesystem behavior and storage faults still require target-environment testing.

```sh
python3 scripts/release/install.py --prefix "$HOME/.local/share/synapse" verify
python3 scripts/release/install.py --prefix "$HOME/.local/share/synapse" rollback
```

Rollback verifies the previous package before activation. A corrupt previous version is never selected. A corrupt current package can be preserved for inspection while activating a verified previous version. Operations use an exclusive OS file lock; a concurrent installer refuses to proceed. A process crash releases that lock automatically. An interrupted stage may remain on disk; do not delete unfamiliar files blindly. Inspect such a stage before cleanup.

`current` is the atomic executable activation boundary. The convenience `previous` pointer is updated separately; a machine failure between pointer changes may require selecting a verified retained version manually. This tooling does not claim a multi-object filesystem transaction or recovery from every storage failure.

## Uninstall and data retention

```sh
python3 scripts/release/install.py --prefix "$HOME/.local/share/synapse" uninstall
python3 scripts/release/install.py --prefix "$HOME/.local/share/synapse" uninstall --keep-releases
```

Uninstall checks that no installed native process is running, verifies installer-owned paths and refuses destructive cleanup if unknown files, modified releases or unsafe links are present. Normal uninstall removes the owned installation. `--keep-releases` removes active entrypoints while retaining verified version directories.

Runtime model caches, configuration and identity keys outside this installation prefix are preserved. The installer does not claim ownership of existing `~/.synapse` or other data directories and does not offer an unsafe blanket purge. Review and explicitly remove those through the runtime's own data controls when that is your intent.

## Executed regression coverage

```sh
python3 -m unittest discover -s scripts/release -p 'test_*.py' -v
```

The suite exercises actual temporary archives, temporary Ed25519 keys, filesystem paths, executable links, concurrent locks and an owned short-lived native process. It covers signature/tamper rejection, traversal/links/duplicate members, target mismatch, failed-update preservation, downgrade policy, rollback, modified-package rejection, uninstallation, foreign-data preservation and deterministic packaging. It leaves the real user installation and configuration untouched.
